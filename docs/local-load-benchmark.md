# 本機探索／推薦負載模擬

執行：`npm run bench:local`。使用目前編譯的 Node HTTP 服務、真實 provider/parser、設定讀取與快取。每個情境啟動新的隔離程序，固定 50 筆遊戲搜尋回應，Steam 單次回應延遲分別設定 100、500 毫秒。所有 Steam 呼叫均由 fixture 攔截，不連接外部網路；不使用現有收藏或房間資料。

原始結果：`artifacts/local-load-baseline.json`。日期、CPU 型號、邏輯核心數、Node 版本與記憶體以 JSON 欄位為準。這裡的冷快取只指新的應用程式程序，不包含清除作業系統檔案快取。

## 候選實驗

歷史候選結果保留於 `artifacts/local-load-bounded-queue.json`，基準保留於 `artifacts/local-load-baseline.json`。以下表格是整合前的單輪實驗，並非最新正式版量測。

三項優化已套用正式原始碼：查詢同時執行 2 個，最多等待 32 個，等待期限 15 秒；滿載或等待超時回覆 HTTP 503 與 Retry-After。進行中請求獨立合併，完成結果採 48 筆 LRU、5 分鐘 TTL（完成時計算）、16 MiB 序列化資料容量上限。此容量不等同 Node 實際堆積記憶體。探索與推薦共用限流，個人排除狀態在回覆時另行套用，不寫入公開結果快取。

首次載入畫面僅預載最近 3 款封面，保留原有高解析圖片解碼與後續有界預載。測試涵蓋排隊滿載、等待超時、重試、快取淘汰、大小與 TTL，以及首批預載上限和取消。

`npm run bench:local` 現在直接量測正式建置，輸出 `artifacts/local-load-production.json`，不再產生或修補隔離編譯副本。測試設定仍置於獨立臨時目錄，結束時自動清除。

## 本次結果

以下為單輪樣本；p95 只計算成功回覆，拒絕數另列。不能把較快的拒絕當成較好效能。

| 情境（上游固定 100 ms） | 目前成功數 | 候選成功數 | 目前成功 p95 | 候選成功 p95 |
| --- | --- | --- | --- | --- |
| 50 個相同條件冷查詢 | 50/50 | 50/50 | 275 ms | 271 ms |
| 20 個不同條件冷查詢 | 2/20 | 20/20 | 255 ms | 2201 ms |
| 預先逐一查過 20 種條件，再並行重查 | 12/20 | 20/20 | 222 ms | 16 ms |
| 50 個相同條件暖查詢 | 50/50 | 50/50 | 32 ms | 36 ms |

- 目前相同條件冷查詢共 2 次模擬上游呼叫，暖查詢為 0。已有效合併相同請求。
- 不同條件冷查詢：目前只完成 2 種條件，共 4 次上游呼叫；候選完成 20 種條件，共 40 次上游呼叫。候選維持最多 2 個同時上游呼叫，主要改善拒絕率，沒有降低首次不同查詢的總工作量。
- 重查 20 種條件：目前仍有 4 次上游呼叫且拒絕 8 次；候選上游呼叫為 0、全部成功。
- 20 個不同遊戲圖文 API 同時請求：目前與候選都是 16/20 成功，候選查詢佇列不會修復這個獨立預載瓶頸。
- 預載量模型：同一服務下首批 8 個圖文 API 對應 16 次上游呼叫；首批 3 個對應 6 次，該階段減少 `(16 - 6) / 16 = 62.5%`。不是整個瀏覽流程減少 62.5%，之後真正看到遊戲仍可能請求資料。此模型不是瀏覽器圖片載入測試。
- 不同條件冷查詢的 Node 取樣 RSS：目前約 99 MiB，候選約 120 MiB。RSS 每 10 ms 取樣；CPU 時間依作業系統精度記錄，短情境可能顯示 0。不能直接對照 Cloudflare Workers 記憶體或 CPU 配額。

## 整合狀態與後續方向

1. 已完成有上限、有期限的查詢等待佇列與滿載回覆。
2. 已完成進行中請求與完成 LRU 分離，限制筆數與序列化大小。

未量測真實 Steam 延遲、429、完整評論路徑、圖片下載／解碼、瀏覽器 FPS、TLS/CDN、Cloudflare isolate、長時間穩態或惡意流量。每種情境只執行一輪；資料支持辨識目前的佇列與快取問題，不支持宣稱可承載多少真實同時在線玩家。
